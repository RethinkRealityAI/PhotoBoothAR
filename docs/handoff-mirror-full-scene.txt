SECOND HANDOFF — the `provider-keys` edge-function contract this client assumes
==============================================================================
VERIFIED 2026-07-29 against supabase/functions/provider-keys/index.ts as written
by Wave 1 — request shape, both envelopes, every field name and every error code
below match, and its maskKeyId is logic-identical to providerKeysModel.maskKeyId
(MASK_VISIBLE 4, '•'.repeat(8) middle), so a server-masked id and an optimistic
client-masked one render the same. NOTHING TO RECONCILE; this section is the
record of the contract, and the mirror-pair note for whoever changes a mask:

REQUEST  POST provider-keys  body: { action, args }
         — the house multi-action convention (admin-api, support-api).
         action 'status' args { provider }                       → read
         action 'set'    args { provider, keyId, keySecret }     → upsert
         action 'clear'  args { provider }                       → delete
         `args.orgId` is sent ONLY when the caller passes one (multi-org member);
         otherwise the function resolves the org from the JWT.
         provider is always the literal 'higgsfield' today (migration 030's
         CHECK constraint allows only that value).

RESPONSE 200 with either `{ data: {...} }` or the bare object — the client
         unwraps `data` when present, so either envelope works. Fields read:
           configured: boolean         — the org has its own key stored
           keyIdMasked: string|null    — masked id, NEVER the secret
           platformAvailable: boolean  — the PLATFORM's own key is configured,
                                         i.e. a host with no key can still
                                         generate on platform credits
           status: 'unverified'|'valid'|'invalid'   (optional)
         Anything missing/mistyped degrades to configured:false,
         keyIdMasked:null, platformAvailable:false — never an invented key.

ERRORS   non-2xx with `{ error: "<code>" }` (+ optional `message`), decoded from
         FunctionsHttpError like ai.ts invokeAi. Codes the client has copy for:
         unauthorized, forbidden, invalid_body, invalid_key, rate_limited,
         internal; transport failures surface as 'network'.

Client-side validation happens BEFORE any round trip (providerKeysModel.ts):
non-empty, ≤200 chars per half, no internal whitespace, and an `id:secret`
paste is split on the FIRST colon. There is deliberately NO format/prefix check
— if Higgsfield changes its key format, the server is the authority.
